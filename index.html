Reverse Engineering happ:// — A Deep Dive

How five generations of link encryption were analysed, from a trivial RSA wrapper to a fully obfuscated native ARM64 library, and reimplemented in pure Python and JavaScript.

Background: The happ:// URI Scheme

The happ:// URI scheme is a custom deep-link protocol used by a mobile application to encode destination URLs as opaque, encrypted payloads. Instead of embedding a plain https:// link that anyone can read, the app generates a payload that is passed to the installed application for decryption. Decryption happens on-device; the server never sees the target URL.

Over time the scheme evolved through five encryption generations — crypt through crypt5 — each substantially harder to reverse-engineer than the previous one. This tool implements all five.

Generations 1–4: RSA-PKCS1v15 in a Loop

The first four link types share the same conceptually simple structure. The payload is a standard Base64-encoded RSA ciphertext split into fixed-size blocks matching the key modulus: 

happ://crypt/<base64( RSA_block₁ ‖ RSA_block₂ ‖ … )>
SchemeKey sizeBlock sizeAlgorithm
cryptRSA-1024128 BPKCS1v15
crypt2RSA-4096512 BPKCS1v15
crypt3RSA-4096512 BPKCS1v15
crypt4RSA-4096512 BPKCS1v15

Each block is decrypted independently with RSA-PKCS1v15 and the plaintext fragments are concatenated to recover the target URL. Longer URLs simply produce more blocks.

The four RSA private keys were found verbatim as Base64 string literals in the application's compiled DEX bytecode — no key derivation, no obfuscation, just hardcoded constants. Extracting them required only a standard DEX disassembler.

Generation 5: The Native Library

crypt5 raises the bar significantly. Decryption is delegated to an ARM64 native shared library (liberror-code.so) loaded via JNI. The Java layer passes in the payload as a byte array and receives back the decrypted URL. All cryptographic logic — key selection, RSA, symmetric cipher — lives inside compiled machine code with no symbol table and no plaintext constants visible in the Java layer.

Step 1 — Reversing via CPU Emulation

Without access to a live ARM64 device running the app, the approach was to use the Unicorn Engine — a lightweight, multi-architecture CPU emulator built on QEMU — to execute the ARM64 machine code directly on an x86-64 host machine. The emulator is initialised with:

  • The library's ELF code and data segments memory-mapped at their original virtual addresses.
  • A synthetic stack and heap, with the payload written into the emulated address space.
  • JNI call sites replaced by trampoline hooks that transfer control to Python handler functions.
  • A hook on the python_get_help JNI function, which the library calls to obtain the RSA key material from the Java layer.
  • A hook on the internal RSA key-loading routine, which captures the fully-expanded PKCS8 private key just before it is passed to the RSA engine.

This produced a working black-box decryptor in pure Python: any valid crypt5 payload in, the decrypted URL out, with no physical device required.

Step 2 — Payload Format Discovery

With the emulator running and instrumented with memory-write hooks, we performed differential analysis: flip one byte of the payload, observe exactly which intermediate buffer bytes change, repeat for every position. This technique mapped every byte of the payload to its precise role:

The Block-Pair Swap Transform

All encoded regions use the same obfuscation permutation. For output position j (1-indexed) from a region of length L: 

k      = (j − 1) ÷ 4
p      = (j − 1) mod 4
source = 4k + (p + 2) mod 4

The net effect is that each 4-character block is rotated by two positions: ABCD → CDAB. Equivalently, the two 2-character pairs within every block are swapped. The transform is its own inverse — applying it twice recovers the original string.

Nonce decoding uses the same pair-swap applied at the 2-character level across three 4-char blocks: 

n     = payload[4:16]
nonce = n[2:4] + n[0:2] + n[6:8] + n[4:6] + n[10:12] + n[8:10]

Step 3 — Key Selection

The library contains 33 RSA-4096 private keys and selects one based on a short selector string derived from a fixed 16-character magic constant ('ikdhaaoxaiilieih'): 

rev      = 'ikdhaaoxaiilieih'[::-1]           # → 'hieiliiaxoaahdki'
selector = ''.join(rev[i+1] for i in range(0, len(rev), 2))  # → 'iiiaoadi'

The selector is matched against 33 condition tuples (starts, mid, ends): 

selector.startswith(starts)   # first 2 chars
selector[2:6] == mid          # middle 4 chars
selector.endswith(ends)       # last 2 chars

The matching tuple identifies which pre-computed RSA key to use. All 33 conditions are stored in data/selectors.json.

The Key Expansion Problem

The python_get_help JNI call returns a 1,612-character encoded key. The native library then internally expands this into a 3,168-character Base64-encoded PKCS8 DER private key before passing it to the RSA engine. Reverse-engineering the proprietary expansion algorithm inside the obfuscated native code would be time-consuming.

Instead, we took a simpler approach: run the emulator once per condition, monkey-patching python_get_help to return each condition's key in turn, and capture the fully-expanded PKCS8 key exactly at the point it is consumed. This produced a complete 33-entry pre-computed lookup table — the data/expanded_rsa_keys.json file (~105 KB) embedded in this tool.

The Full crypt5 Decryption Pipeline

payload
  ├── parse nonce (12 bytes after block-pair-swap inversion)
  ├── parse N, url_b64 (N bytes, block-pair-swap inverted)
  └── parse enc_str (684 bytes, block-pair-swap inverted)

locate non-trailing '=' in enc_str → RSA ciphertext (512 bytes)

RSA-PKCS1v15 decrypt (4096-bit key from expanded_rsa_keys.json)
  → 44-char base64 string

swapPairs(rsa_plain) → base64-decode → 32-byte ChaCha20 key

ChaCha20-Poly1305 decrypt(url_ciphertext, nonce, chacha_key)
  → intermediate bytes

swapPairs(intermediate) → base64-decode → final URL ✓

Note that swapPairs (used in the final two steps) is a different, simpler transform from the block-pair swap used in the payload encoding. SwapPairs swaps adjacent character pairs throughout the entire string: ABCD → BADC.

From Emulator to Pure Code

Once the full pipeline was mapped and verified against multiple test vectors, the Unicorn emulator was no longer needed. The Python implementation in decryptor/decrypt_crypt5_pure.py and this browser tool implement the identical algorithm entirely from scratch — no ARM64 emulation, no liberror-code.so, no native dependencies of any kind. The only artifact retained from the emulation phase is the pre-computed 33-entry RSA key table.

On the browser side, two library choices needed careful consideration:

  • RSA-PKCS1v15 decryption — the Web Crypto API does not support PKCS1v15 decryption (only OAEP and PSS), so node-forge is used instead.
  • ChaCha20-Poly1305 — provided by @noble/ciphers, a modern, audited, zero-dependency cryptography library.

Both are bundled at build time by Vite — no CDN requests at runtime, no CORS issues, no version-skew surprises. The CDN URL approach used in earlier prototypes broke because @noble/ciphers' jsdelivr distribution doesn't re-export named symbols from sub-paths the same way the npm package does when bundled.

All processing runs locally in your browser — no data is transmitted to any server.
