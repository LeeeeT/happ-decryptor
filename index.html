Reverse Engineering happ:// — A Deep Dive

How five generations of link encryption were analysed and reimplemented — from a trivial RSA wrapper to a fully obfuscated native ARM64 library guarding 33 different private keys.

Background: The happ:// URI Scheme

The happ:// URI scheme is a custom deep-link protocol used by a mobile application to encode destination URLs as opaque, encrypted payloads. Instead of embedding a plain https:// link that can be read by anyone who intercepts or inspects the link, the app generates a payload that only the installed application can decrypt. Decryption happens entirely on-device; the server never sees the destination URL in plaintext.

The scheme evolved through five encryption generations — crypt through crypt5 — each substantially harder to reverse-engineer than the previous one. This tool implements all five.

Generations 1–4: Hardcoded RSA Keys

The first four generations share the same conceptual structure. A target URL is encrypted with RSA-PKCS1v15, split into fixed-size blocks matching the key modulus, and the concatenated ciphertext is Base64-encoded: 

happ://crypt/<base64( RSA_block₁ ‖ RSA_block₂ ‖ … )>
SchemeKey sizeBlock size (bytes)Algorithm
cryptRSA-1024128PKCS1v15
crypt2RSA-4096512PKCS1v15

crypt4RSA-4096512PKCS1v15

Decryption is symmetric: split the Base64 payload back into 128-byte (crypt) or 512-byte (crypt2–4) blocks, decrypt each block independently with RSA-PKCS1v15, and concatenate the plaintext fragments to recover the URL.

Each of the four RSA private keys is stored verbatim as a Base64 string literal inside the application's compiled DEX bytecode — no derivation, no obfuscation. The keys are used directly by the Java runtime via the standard JCA API.

Generation 5: The Obfuscated Native Library

crypt5 is a different beast. Decryption is delegated to a stripped ARM64 native shared library loaded via JNI. The Java layer passes the payload as a byte array and receives the decrypted URL back; every cryptographic operation — including key storage, key selection, and both the RSA and symmetric cipher — is hidden inside machine code with no exported symbols, no readable string constants, and no meaningful structure visible to a Java-layer observer.

Payload Obfuscation: The Block-Pair Swap

Before any cryptography can happen, the payload must be decoded from its wire format. All variable-length regions in a crypt5 payload are shuffled using a fixed permutation that we call the block-pair swap. For output position j (1-indexed) within a region: 

k      = (j − 1) ÷ 4
p      = (j − 1) mod 4
source = 4·k + (p + 2) mod 4

The net effect is that every 4-character block is rotated left by two positions — equivalently, the two 2-character pairs within each block swap places: AB CD → CD AB. The transform is an involution (its own inverse), so decoding and encoding are the same operation.

Payload Structure

The full wire format of a crypt5 payload was recovered through differential analysis: by systematically varying individual bytes and observing which internal buffers changed, every field was mapped to its precise offset and role.

Nonce extraction applies the pair-swap at the 2-character pair level across three 4-character blocks of payload[4:16]: 

n     = payload[4:16]
nonce = n[2:4] + n[0:2]  +  n[6:8] + n[4:6]  +  n[10:12] + n[8:10]

The RSA ciphertext region contains a non-trailing '=' character that acts as a delimiter; everything after it is the Base64-encoded 512-byte RSA ciphertext.

Key Selection: 33 Keys, One Selector

The native library embeds 33 distinct RSA-4096 private keys. To decide which one to use for a given link, it evaluates a short selector string derived from a fixed 16-character constant baked into the library: "ikdhaaoxaiilieih".

The derivation reverses the string, then picks every second character starting from index 1: 

reversed  = "ikdhaaoxaiilieih"[::-1]        → "hieiliiaxoaahdki"
selector  = reversed[1] + reversed[3] + …   → "iiiaoadi"

The selector is then tested against 33 stored condition tuples (starts, mid, ends) until one matches: 

selector.startswith(starts)      # checks first 2 characters
selector[2:6] == mid             # checks the middle 4 characters
selector.endswith(ends)          # checks the last 2 characters

The matching condition identifies the RSA key to use. Because the selector is derived from a compile-time constant, it never changes — the same key is always selected for all crypt5 links. The 33 conditions exist to support different build variants of the app. All conditions and their corresponding pre-computed keys are bundled in this tool's data/ directory.

Key Encoding and Expansion

The native library does not store raw PKCS8 DER key material directly. Instead, the Java layer supplies a 1,612-character encoded key string via a JNI callback. The library internally transforms this into a 3,168-character Base64 string, then decodes it to recover the actual PKCS8 DER private key before passing it to the RSA engine.

The expansion algorithm is proprietary and deeply obfuscated in the stripped binary. Rather than reversing it, we obtained the fully-expanded keys directly by observing the key material at the exact point of consumption — capturing the DER bytes as they are loaded into the RSA engine for each of the 33 conditions. The resulting 33-entry lookup table (~105 KB) is what this tool uses.

The Full crypt5 Decryption Pipeline

crypt5 payload string ├─ strip magic prefix ("iaii") and variable suffix ("adi" / "cadi" / "lkadi" / …) ├─ read N = int(payload[18:20]) ├─ nonce = block-pair-swap(payload[4:16]) → 12-byte ChaCha nonce ├─ url_b64 = payload[17] + block-pair-swap(payload[20:20+N]) → N chars (Base64 URL ciphertext) └─ enc_str = separator + block-pair-swap(payload[20+N:…]) → 684 chars (encoded RSA ciphertext) locate non-trailing '=' in enc_str → everything after it is the RSA ciphertext in Base64 base64-decode RSA ciphertext → 512-byte RSA ciphertext derive selector from "ikdhaaoxaiilieih" → look up 4096-bit RSA private key in table RSA-PKCS1v15.decrypt(ciphertext, key) → 44-char Base64 string swapPairs(rsa_plaintext) → base64-decode → 32-byte ChaCha20 key (swapPairs: every adjacent character pair is swapped — ABCD → BADC) base64-decode(url_b64) → URL ciphertext + 16-byte Poly1305 tag ChaCha20-Poly1305.decrypt(ciphertext, nonce, key) → intermediate string swapPairs(intermediate) → base64-decode → final URL ✓

Two distinct string transforms appear in this pipeline and must not be confused. The block-pair swap operates on 4-character blocks and swaps the two 2-char halves of each block (AB CD → CD AB); it is used to decode all three payload fields. The simpler swapPairs operates on the whole string and swaps every adjacent pair of characters (ABCD → BADC); it is applied to the RSA plaintext (to derive the ChaCha key) and to the ChaCha output (before the final Base64 decode).

Browser Implementation

The entire pipeline runs in your browser with no server involvement. Two cryptographic dependencies are needed, both bundled at build time:

  • RSA-PKCS1v15 decryption — the Web Crypto API supports only OAEP for RSA decryption and cannot handle PKCS1v15, so node-forge is used instead.
  • ChaCha20-Poly1305 — provided by @noble/ciphers, a modern, audited, zero-dependency cryptography library.
All processing runs locally in your browser — no data is transmitted to any server.
